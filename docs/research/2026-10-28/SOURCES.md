## How findings were handled

- A baseline audit inspected current macOS, Android and Linux source without a favored defect hypothesis. Separate audits inspected cleanup/context and delivery/platform implementations. Root inspected speech/model/file/automation/mobile architecture. All application work was read-only.
- New opportunities were checked against current symbols, schemas, callers and tests. The strongest counterargument and deliberate product boundary are included in the evidence dossiers. “HOLDS” refers to the narrow source distinction in that section; it is not a measured benefit or defect verdict.
- Formatting metrics received a separate refutation pass. Paragraph-only differences disappear from zero-edit and WER; punctuation/case do not disappear from all reported metrics. Existing policy/delivery unit tests are meaningful counterevidence. The final recommendation is consequently narrow.
- Cross-dossier duplicates were merged in the 48-entry backlog: desktop cleanup retry, file transcription, Android RecognitionService and Android model/language selection each appear once there. Plain-text export and timed/structured export are separate scopes.
- Static inspection cannot establish actual speed, quality, paste acceptance, app compatibility, battery use, signed-release availability or model eligibility. Recommendations that depend on these are experiments with acceptance criteria. No competitor marketing multiplier was adopted.
- Existing Android is an initial, uncommitted implementation. Its README's earlier emulator results are attributed historical checks, not tests rerun by this research. Linux's hardware qualification is explicitly still open in its own verification document.
